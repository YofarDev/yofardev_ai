**Goal:** close the M4–M6 band: Wow #1 and Wow #2 *played by the running macOS app* (not

in front of the avatar; the manual M5 gates run by `frive.sh`; the emulator budget re-checked with

taught tool-call rounds), a `say`-backed `TtsSynthesizer` and a slow canned weather tool, then grabs
the render view's layer every frame.

**Tech stack:** Dart 3.8 / flutter_bloc / freezed; Python generators → RML → Rive CLI 1.8.0;
`rive` 0.14.11 / `rive_native` 0.1.11; macOS `say` and Homebrew `ffmpeg` (already on the host) for

## Rulings (2026-10-30, autonomous; the owner may overturn any of them)

1. **The wows are played by the real app, captured headless.** A probe (2026-10-30) showed
   `OffsetLayer.toImage` on the macOS render view captures the Rive scene and the avatar (Rive
   renders into a texture the snapshot includes), at ~0.6 s per PNG-encoded frame, so frames are
   grabbed as raw RGBA and encoded afterwards. The harness is `integration_test/wow_capture_test.dart`
   (macOS only, not in `fverify.sh`): it boots `setupServiceLocator` + `bootstrapApp` + `App` like
   `frame_cost_test.dart`, types the user's line into the real composer, sends it, and lets the real
   pipeline run (chat → streaming → tool → director → TTS queue → `ChatTtsCubit` → `SpeechAnalyzer`
   → `FacePerformer` → `RiveAvatarView`). No screen capture, no computer use: the window only has to
   stay unoccluded (AGENTS.md gotcha), which `flutter test -d macos` arranges by opening it in front.
2. **No real LLM call, no owner data touched.** `SharedPreferences.setMockInitialValues` gives the
   run an in-memory store holding one dummy LLM config (endpoint `http://127.0.0.1:9`, never
   reached) and English as the chat language, so the owner's chats, configs and keys are neither
   read nor written. In debug `LlmServiceInterface` already resolves to `FakeLlmService`; M6 fixes
   its one leak: `generateTitle` delegated to the real service even while a script is active (a new
   chat's first message would have made a real title call). While active it now returns the
   script's title (or null) without a call. The harness asserts that no HTTP request leaves the
   process (`HttpOverrides` that throws).
3. **Scripted tool calls.** `FakeLlmResponse` gains an optional `toolCalls` list
   (`FakeToolCall(name, arguments)`); such a response streams as `toolCallDelta` chunks then
   `complete()`, so the real streaming service runs its tool round and asks the fake again for the
   answer round (two queued responses per tool reply). The tool itself is not faked in the fake LLM:
   the harness injects a `ToolRegistry` whose `getCurrentWeather` waits 2.5 s (the storyboard's
   "while the tool runs") and returns a canned Tokyo result; the real weather tool needs the owner's
   OpenWeather key and is never called.
4. **Real audio, canned voice.** Supertonic's ONNX models are not in the repo or on this Mac (they
   are gitignored), so on-device TTS cannot run here. The harness's `TtsSynthesizer` runs macOS
   `say -v Samantha --file-format=WAVE --data-format=LEI16@24000` per sentence (verified: RIFF PCM
   format 1, mono, which `wav_pcm.dart` reads) and keeps a copy of each WAV for the muxed MP4.
   Everything downstream of the WAV (amplitudes, `SpeechAnalyzer`, G2P alignment, visemes, pre-roll
   breath) is the app's own code.
5. **DI seam for the harness.** `setupServiceLocator` gains optional named overrides
   `{TtsSynthesizer? ttsSynthesizer, ToolRegistry? toolRegistry}`; null keeps today's wiring. The
   eager `AvatarCueService` resolution builds the pipeline inside setup, so re-registering after it
   is not an option (it would split the tool-activity stream). Production passes nothing.
6. **What the harness records.** Per captured frame: the elapsed time and an app-state sample
   (`TalkingState.phase`, `ChatState.activeTool`, the director's intent `prop` and head yaw, the
   performer's current `FaceFrame` jaw / lipPress / browInnerUp / browOuterUp / breath / lean, the
   caption line). Written as `timeline.json` beside the raw frames in the app's caches folder
   (`~/Library/Caches/fr.yofardev.yofardevAi/wow/<wow>/`); `rive/tools/wow_capture.py` turns them
   into a GIF (15 fps, 360 px wide), an MP4 with the sentence WAVs muxed at the times their caption
   appeared (`ffmpeg`, `adelay`), a beat contact sheet, and `gates.txt`. A second pass per wow
   (`CAPTURE=0`) records `FrameTiming` without grabbing frames (grabbing inflates raster).
7. **Wow gates (objective, from the timeline):**
   - Wow #1 (campfire, `WorldStateService.setRain(1)` set by the harness, standing in for M7–M9
     world sync): the scene is campfire with rain 1 the whole run; `lean` > 0.3 while the user types
     (composer activity); `breath` > 0.5 within 400 ms before the first audio; closed mouths
     (`lipPress` ≥ 0.5, jaw ≤ 0.1) while speaking, counted as separate runs, ≥ 0.7 × the number of
     words starting with p / b / m (word times from the alignment are not exposed, and neighbouring
     bilabials such as "big bright" may share one closure); brows up (`browInnerUp` + `browOuterUp` ≥ 0.3) in the last 600 ms of the
     question sentence; the front rain layer visible (frame pixels in the front band differ from a
     rain-0 frame) — and every frame non-empty.
   - Wow #2 (livingRoom): `activeTool == getCurrentWeather` for ≥ 2 s; the intent prop is tablet
     while it runs and none within 1 s after the answer starts; head yaw |≥ 0.3| while the tool
     runs and |≤ 0.15| while answering; speaking phase after the tool; every frame non-empty.
   The script lines: Wow #1 user "Can you tell me a story by the fire?" → reply with p/b/m-dense
   words ending on a question ("Picture a big bright moon above the pines. Maybe the rain will pass
   by morning. Do you hear the logs hissing?"); Wow #2 user "What's the weather in Tokyo?" →
   tool round `getCurrentWeather {"location":"Tokyo"}` → "It's eighteen degrees in Tokyo, light
   rain and a soft breeze. Bring an umbrella!" with `[g:nod]` on the first sentence.
8. **Weather in front of the avatar: a `SceneFront` artboard (contract v9).** The scene and the
   avatar are two files; a third file would load and decode separately per scene. Instead a scene
   file may carry a second artboard `SceneFront` (1080 × 1920, state machine `Main`, the same
   `SceneVM`), which the app draws *above* the avatar with the same `Fit.cover`. Only campfire and
   beach have one (outdoor rain): a near rain sheet (fewer, longer, wider, fainter streaks than the
   back sheets, gain 1.25 parallax: nearer than Plane5), a rain mist veil of `lightFog` rising from
   the bottom (density 0.18 × rain), and a splash band at the bottom edge, all at opacity `rain`.
   livingRoom's rain is outside the window (the avatar is indoors) and deepSpace ignores rain: no
   front artboard. No dry fog goes in front: M5 put fog veils only in front of Plane0–2, and the
   avatar stands among the near planes, so the dry look stays exactly M5's.
9. **The front layer costs nothing dry.** The scene view creates the front controller only while
   the loaded file has `SceneFront` *and* rain > 0.001, and drops it when rain returns to 0 (the
   layer is invisible at 0, so mounting and unmounting is seamless). It is wrapped in
   `IgnorePointer`, so avatar and prop taps go through. It gets rain and parallax from the same
   writers as the back artboard.
10. **Automated gates in `frive.sh`.** After the build and the contract check, `frive.sh` runs
    `rive/tools/rive_gates.py` for the scenes it built: `review_diorama.py --gates-only` per scene
    (parallax corners, plane travel, pointer proofs, rain wet/seam, the new front-layer gates; no
    images written) and `motion_review.py --gates-only` (the tablet and newspaper pop, seam and IK
    gates). Any `FAIL` fails the build. `FRIVE_GATES=0 ./scripts/frive.sh` skips them (they add a
    few minutes of sequential renders). The fairing and lint gates stay where they are (pytest,
    `check_contract.py`).
11. **Device budget.** The emulator profile run (M5 ruling 10, same AVD and commands, never
    `192.168.1.169:5555`) repeats with M6: every scene, campfire and beach at rain 1 (front layer
    on). The mid-tier run is the owner's: `rive/review/m6/device/README.md` gives the exact command
    and pass thresholds — per scene and at rain 1: frames over 16.6 ms (build or raster) ≤ 1 %,
    build P95 ≤ 14 ms, raster P95 ≤ 14 ms.
12. **Props cut.** The window glance contradicts the signed Wow #2 storyboard (weather → tablet; M5
    ruling 9) and the telescope belongs to the deepSpace journey (M7–M9). The 40 KB left under the
    avatar budget is kept for hands. Not built.
13. **Mouth fixes only if cheap and objective** (Task 8): the "sticker" outline (the closed mouth
    line as heavy as the silhouette) and lipTuck ≈ lipPress. Each needs a numeric gate that the M5
    file fails and the fix passes; if a fix moves more than the mouth (any pixel outside the mouth
    box at rest) or costs > 3 KB, it is dropped and recorded.
14. **Review loop (owner, as M5 ruling 11):** no critic rounds, no score gate. Each visual change
    renders its evidence once into `rive/review/m6/`, gets at most one cheap Sonnet self-check for
    objective defects, fixes those, and adds one line to `rive/CRITIC_ITERATIONS.md` § "M6".
15. **Implementers:** Claude subagents (Sonnet where enough) for `[zcode]` tasks; Rive builds one at
    a time; the capture runs one at a time (one macOS app window).
16. **Not in M6:** a real mid-tier device and battery (the owner's run), real Supertonic voices on
    macOS, real tool data on the tablet screen (placeholder glyphs), world sync, window glance,
    telescope, hands, Kokoro, nested VMs, the schema-generated contract, Wow #3.
